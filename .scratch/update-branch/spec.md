# 更新分支：把其他分支合并/变基进当前分支

Status: ready-for-agent

## 问题陈述

面板目前只能通过 pull（`--ff-only`）快进拉取**上游**更新。当用户的当前分支需要吸收**任意其他分支**（本地特性分支、同事推送的远端分支）的更改时，必须离开面板去终端敲 `git merge` / `git rebase`。合并方向、影响范围全靠手打命令，面板既不引导也不兜底，误操作（方向搞反、冲突措手不及）时有发生。

## 方案

在分支面板提供「更新分支」对话框：用户选择一种操作（**合并**——用一个合并提交吸收来源分支并保留历史；**变基**——把当前分支的提交移到目标分支之上形成线性历史），再选择来源分支。执行前对话框展示合并方向（来源 → 目标）、将带入/移动的提交数，合并操作还附 `git merge-tree` 冲突预检；确认后才执行。冲突发生时列出冲突文件并提供一键「中止」回到操作前状态。全程不自动 push。

## 用户故事

1. 作为面板使用者，我想把另一个分支合并进当前分支，以便不离开面板就能吸收其他分支的工作成果。
2. 作为面板使用者，我想把当前分支变基到另一个分支之上，以便保持线性提交历史。
3. 作为面板使用者，我想在执行前看到「来源 → 目标」的明确方向文案，以便确认自己没有把合并方向搞反。
4. 作为面板使用者，我想在合并前看到将带入的提交数量，以便预判这次合并的影响范围。
5. 作为面板使用者，我想在变基前看到当前分支有多少提交将被移动，以便预判变基的规模。
6. 作为面板使用者，我想在合并前看到冲突预检结果（哪些文件会冲突），以便提前安排冲突处理而不是事后救火。
7. 作为面板使用者，我想在冲突预检不可用（git 版本不支持）时仍能正常发起合并，以便不受 daemon 机器 git 版本限制。
8. 作为面板使用者，我想选择远端分支（如 origin/feat/x）作为来源，以便吸收同事已推送的更改。
9. 作为面板使用者，我想在两个操作方式之间明确二选一，以便清楚知道这次产生合并提交还是线性历史。
10. 作为面板使用者，我想一键重置对话框里的选择，以便从干净状态重新选分支。
11. 作为面板使用者，我想在未选择来源分支时确认按钮保持禁用，以便避免误触发空操作。
12. 作为面板使用者，我想在把当前分支自己选为来源时被阻止，以便避免无意义的自我合并/变基。
13. 作为面板使用者，我想在合并发生冲突时看到冲突文件清单，以便知道去哪里解决冲突。
14. 作为面板使用者，我想在合并/变基卡在冲突态时一键「中止」，以便回到操作开始前的状态而不必去终端敲 abort。
15. 作为面板使用者，我想在重新打开面板后仍能看到存在进行中的合并/变基并可中止，以便隔了一段时间也不会遗忘中断的操作。
16. 作为面板使用者，我想在工作区有未提交更改时被明确拒绝并提示原因，以便先提交或贮藏再执行合并/变基。
17. 作为面板使用者，我想在操作成功后看到分支最新的 ahead/behind 与提交历史刷新，以便立即确认操作结果。
18. 作为面板使用者，我想合并/变基成功后**不**被自动推送，以便由我自己决定何时把结果同步到远端。
19. 作为面板使用者，我想在中文与英文界面下都看到对应语言的操作文案，以便和面板其他部分保持一致的阅读体验。
20. 作为面板使用者，我想悬停在入口按钮上看到功能提示，以便了解这个按钮做什么。

## 实现决策

**契约（shared schema）**

- `actionSchema` 新增三个 kind，走现有 `git.action` RPC，不新建 RPC 通道：
  - `merge`：`{ kind: "merge", branch }` —— 服务端执行 `git merge --no-ff --no-edit <branch>`。固定产生合并提交（截图文案「使用合并提交合并分支，并保留历史」的语义），不提供 squash / ff 选项。
  - `rebase`：`{ kind: "rebase", onto }` —— 服务端执行 `git rebase <onto>`（把当前分支移到 onto 之上）。仅支持分支头，不支持变基到任意提交。
  - `abort`：无参数 —— 服务端检测仓库状态后执行 `git merge --abort` 或 `git rebase --abort`；两者都不在时报 invalid-action 类错误。
- 分支名按现有 action 惯例信任字符串：git 以 argv 数组执行（无 shell 注入面），ref 不存在落入现有 `not-found` 错误码。
- 选定分支等于当前分支时，服务端拒绝（invalid-action），前端也预先禁用。

**快照扩展**

- 分支快照新增合并/变基进行中状态字段（`merging` / `rebasing` / 空），服务端通过 `MERGE_HEAD` 与 rebase 状态目录检测。冲突态时 changes 视图已能显示 conflicted 文件（现有能力，不改动）。

**冲突反馈**

- 合并/变基因冲突失败时，错误输出附带冲突文件清单（从 git stderr 的 CONFLICT 行解析），复用现有 `conflict` 错误码；前端 toast 展示清单，changes 视图可看到冲突文件本体。
- 冲突的**解决**不在面板内进行（见范围外）；面板提供的是「中止」。

**预检（新查询 RPC）**

- 新增一个独立的预检查询 RPC（输入：来源分支 + 操作；输出：带入提交数、被移动提交数、冲突文件列表或 null、预检是否可用）。
- 提交数：合并用 `rev-list --count HEAD..<source>`，变基用 `rev-list --count <onto>..HEAD`。
- 冲突预检：仅合并支持，用 `git merge-tree --write-tree`（无副作用预演）；git 版本不支持或预检失败时返回「不可用」，前端降级为只显示方向与提交数，**不阻塞**执行。
- 变基没有 dry-run 能力，不做冲突预检。
- 前端在用户选定分支后查询预检，未选时不查。

**UI（client）**

- BranchesPane 工具区（现有「新建分支」「刷新」IconButton 旁）新增「更新分支」入口按钮 + hint 文案（按钮 hint 覆盖测试会强制要求）。
- 对话框（复用现有 Modal 组件与 reset/revert confirm 的形态先例）：标题「更新分支」，副标题含当前分支名；操作二选一卡片（合并为默认选中 / 变基）；来源分支下拉合并本地与远端列表，远端分支传完整 ref；预检信息区展示方向文案与提交数；底部「重置」（清空选择）与确认按钮（未选分支禁用）。
- 打开对话框时若快照显示合并/变基进行中，直接呈现「进行中」态：说明 + 冲突文件提示 + 「中止」按钮。
- 成功后沿用 `runAction` 统一行为：返回新快照（ahead/behind、历史自动刷新），git 输出截断展示。**不触发 push**。

**文案**

- `strings.ts` 双语言（en + zh）新增全部对话框与提示 key，与现有翻译机制一致。

**安全边界**

- 脏工作区直接拒绝：复用现有 `local-changes-block` 错误码，不做 `--autostash`。
- 不自动 push；变基已推送分支后 push 被拒属预期，由现有 `push-rejected` 错误码兜底，面板不加拦截。

## 测试决策

- 只测外部行为：schema 契约与组件渲染回调，不测 git 命令拼装的内部细节。
- Schema 契约测试（先例：settings-schema 测试）：三个新 kind 的合法用例接受、空分支名/缺字段拒绝、abort 无参数。
- UI 渲染测试（先例：branches-pane 测试，testing-library + jsdom）：
  - 入口按钮渲染且带 hint；
  - 对话框默认态：合并选中、确认禁用；
  - 选分支后确认回调携带完整参数（正确的 kind 与分支名，远端 ref 原样传递）；
  - 当前分支作为来源时确认禁用；
  - 进行中态：中止按钮渲染并回调 abort；
  - 预检区渲染方向文案、提交数；预检不可用时降级不报错。
- 服务端 git argv 不新增单测接缝（与 pull/push/revert 等现有 action 一致，测试基建未 stub execCommand），靠 typecheck + schema 契约 + 真实仓库人工验收（合并/变基/冲突中止各走一遍）。
- 回归：现有全部测试 + `npm run typecheck` 保持通过。

## 范围外

- 面板内解决冲突与继续操作（标记 resolved、`merge --continue` / `rebase --continue`）——冲突需在终端或外部工具解决，面板只负责发起、查看与中止。（**已由 `.scratch/conflict-resolution/` 承接，见该目录 spec**）
- squash 合并、fast-forward / ff-only 合并选项（上游快进仍由现有 pull 承担）。
- interactive rebase、`--autostash`、变基到任意提交。
- 合并/变基后的自动 push。
- cherry-pick、跨仓库/子模块的特殊合并处理。

## 补充说明

- 对应操作者的合并铁律：任何合并动作必须先报出「哪个分支合到哪个分支、方式、影响提交数、已知冲突」，确认后才执行，且不自动推送——本对话框的方向文案 + 提交数 + 冲突预检 + 确认按钮即该铁律的产品化。
- 参考形态来自外部 Git 工具的「更新分支」对话框截图（合并/变基二选一卡片 + 分支下拉 + 重置/确认），交互照此还原。
- merge-tree 预检依赖 git ≥ 2.38；老版本降级为不可用，属已知取舍。
- **UI 原型拍板（2026-11-17）**：三变体原型（A 卡片式 / B 面板密度列表式 / C 两步向导）对比后拍板 **A 卡片式**（即截图基线形态），预检块、进行中/冲突态、脏工作区警示的呈现以原型 A 为准。完整三变体原型（`.scratch/update-branch/prototype.html`）作为 primary source 留存在 `prototype/update-branch` 分支，不进 main。
