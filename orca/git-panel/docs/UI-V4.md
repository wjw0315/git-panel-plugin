# Orca Git 面板 · UI 交互稿 v4

Status: **implemented → v4.1**（2026-11-21：先落地单页卡片，后按用户改稿把卡片标题挪成顶部页签）。门禁 tsc 0 / 38 测试全过 / plugin check 7 场景 0 issue。上一版（v3）见 [`UI-DESIGN.md`](UI-DESIGN.md)。
可点原型：[`ui-v4.html`](ui-v4.html)（卡片式，保留作对照；`?w=640` 看宽档）。

**方向**：视觉语言走「内置 Source Control 影子」派；交互走单页 + **顶部页签切换**（v4.1 改稿），不再有返回键；面板可拉宽（三档见 §3b，宿主暂未暴露宽度）。

## 1. 为什么重做（v3 的偏差）

v3 是「把内置 Source Control 1:1 抄下来」。照抄带来三个结构性代价：

| v3 的问题 | 后果 |
|---|---|
| 五个平级页（变更 / 历史 / 贮藏 / 分支 / 更多） | 每次看历史都要离开工作区，还得靠「返回更改」找回来；上下文丢失 |
| 已暂存和未暂存在最下方两组，提交框在最上方 | 眼睛要在「写信息」和「我到底暂存了什么」之间来回跳；提交前无法一眼确认内容 |
| 基准分支藏在「更多」页里 | 最需要的那一条信息（要不要先同步）要多点两下才看得到 |
| 13 个远端动作铺成一页 | 一屏都是低频按钮，高频的提交/推送被稀释 |

v4 的判断：**面板不是缩小版的 IDE 侧栏，是一张「提交前确认单」。** 用户打开它的 90% 目的是：看清楚将要提交什么、然后提交。

## 2. 核心不变量（整个设计只有这一条）

> **一个文件要么在「更改」卡里，要么在「提交」卡里。暂存 = 文件从下往上移动；取消暂存 = 从上往下移动。**

这条不变量替代 v3 的「两个分组都堆在页面下半部分」。它的好处：
- 提交卡里列出来的，就是这次提交的真实内容 —— 不需要另外确认。
- 暂存动作有肉眼可见的结果（行在动），不需要 toast。
- 「暂存了多少」不是数字展示，而是列表本身。

## 3. 布局

**v4.1（2026-11-21 用户改稿）**：把那七行卡片标题挪到**顶部做页签**，一次只显示一页内容；卡片折叠模型取消。

```
┌ GIT ─────────────────────────────────────────┐
│ ① [主仓库 · geer2-xforms ▾]  ⎇ main ▾  ⟳  ● │
│    ↑2 ↓0 · origin/main   [基准领先 3] PR #128 │
│ ② 冲突条（仅冲突时，永远在最上）                │
│ ③ 提交 3 │ 更改 23 │ 基准 │ 历史 20 │ 贮藏 0 │ … │  ← Tabs
├───────────────────────────────────────────────┤
│ （当前页内容）                                  │
│                                               │
└───────────────────────────────────────────────┘
```

- 页签顺序：`提交` → `更改` → `基准` → `历史` → `贮藏` → `分支` → `更多`。
- 页签标签带计数：`提交 3`、`更改 23`；为 0 时只显示名字。
- 选中页按插件记忆；切到「历史」「分支」时顺带刷新。
- 冲突条不占页签，永远压在页签上方。
- **更改页的展示方式**：右上角下拉切 `树形` / `平铺`，按插件记忆。树形的目录行是**单行**（展开箭头 + 名字 + 文件数 + 目录级暂存/丢弃全在一行），子项靠 `Box paddingX` 逐层缩进，文件行只写文件名；平铺才在副行写目录。目录展开状态按插件记忆。
- 面板宽度紧张时页签条可横向滚动（宿主 Tabs 行为），标签用 2 字短名。

下面是原 v4 的卡片式骨架，保留作为「为什么先做卡片、后改页签」的记录。

```
┌ GIT ───────────────────────────────────────┐
│ ① [主仓库 · geer2-xforms ▾]   ⎇ main ▾     │  仓库 + 分支，一行
│    ↑2 ↓0 · origin/main    ● 有改动   [···] │  只在有内容时出现第二行
├────────────────────────────────────────────┤
│ ② 冲突条（仅冲突时）                         │
│    合并进行中 · 2 个文件                     │
│    ! src/a.ts        [保留我方][保留对方][标记已解决] │

├────────────────────────────────────────────┤
│ ③ 提交                                       │  ← 默认展开

│    已暂存 2 个文件            [+18 −4] [🗑] │
│      M worker.ts      src    [−][<>][↗]     │
│      A ui-v4.html     docs   [−][<>][↗]     │
│    [ 提交 ]  [▾]     需要提交信息            │

│    ? notes.md         —      [+][🗑][↗]     │
│    ▸ src/ 3 个文件（目录级批量）             │
├────────────────────────────────────────────┤
│ ⑤ 基准 origin/main · 领先 3            [▾]  │  ← 默认收起
│    9f8e7d6 feat: base moved on              │
```

宽度 280–420px 单列，永远不横向滚动。**没有页签，没有「返回」按钮。**

### 3b. 面板可拉宽：三档

面板宽度由用户拖动决定，交互按三档设计（原型 `?w=640` 可直接看宽档）：

| 档 | 宽度 | 行结构 | 差异预览 |
|---|---|---|---|
| 窄 | < 480 | 两行：文件名 / 目录 | 行内展开 |
| 中 | 480–559 | 一行：`src/worker.ts`（目录淡色） | 行内展开 |
| 宽 | ≥ 560 | 一行，行数列右对齐 | **右栏预览**：左列卡片，右列 diff / 提交详情 |

宽档的右栏不是新页面，是「当前选中项」的预览：选文件看 diff，选提交看变更文件，取消选中回空态。窄档保持行内展开，因为 320px 里没有第二栏的位置。

> **落地限制（2026-11-21 实测）**：Orca components 面板没有把面板宽度暴露给插件，`orca` API 里也没有容器宽度钩子。所以当前只实现了窄档（单列 + 行内 diff）；中/宽档要等宿主给宽度信号，或在 `ui.has(...)` 出现宽度能力后再补。

## 4. 卡片目录

| # | 卡片 | 默认 | 卡头右侧 | 展开后 |
|---|---|---|---|---|
| ① | 仓库 + 分支 | 常驻 | 脏点、`···`（更多远端动作） | 仓库下拉；分支下拉（切换/新建/删除） |
| ② | 冲突 | 仅冲突时出现，永远在提交卡之上 | 冲突文件数 | 每个文件一行解决动作 + 中止/继续 |
| ③ | 提交 | 展开 | 已暂存文件数、`+a −b`、丢弃 | 信息框、amend、已暂存列表、提交按钮 + `▾` |
| ④ | 更改 | 展开 | 文件数、全部暂存、全部丢弃 | 文件行、目录折叠 |
| ⑤ | 基准 | 收起 | `领先 N` / `已合入` | 前 5 条提交 + 拉取 |
| ⑥ | 历史 | 收起 | 提交数 | 过滤器、提交列表、加载更多、点开看文件 |
| ⑦ | 贮藏 | 收起 | 条数 | 新建（含未跟踪）、应用/弹出/删除 |
| ⑧ | 分支 | 收起 | 本地分支数 | 切换 / 新建 / 删除 |

卡片头一行固定格式：`标题 · 数量` + 右侧摘要 + 右侧动作。收起时只有这一行（约 28px），所以八张卡全部收起也只占 8 行。

## 5. 交互流程

### A. 打开面板（80% 的场景，目标 3 秒内完成提交）

1. 眼睛落在 ③ 提交卡的「已暂存 N」——**N=0 时整张卡塌成一行**：`提交 · 还没有暂存的更改`，信息框不渲染。
2. 有暂存才展开：写信息 → `⌘Enter` 或点「提交」。
3. 提交成功：③ 回到塌陷态，④ 里的文件消失，头部脏点消失。

### B. 只提交一部分

1. 在 ④ 更改里点某行的 `+`。
2. 该行**当场从 ④ 消失、出现在 ③ 的已暂存列表末尾**（带动画：高度 120ms 收起 + 目标位置展开）。
3. 反向操作：③ 里点 `−`，行回到 ④ 的对应目录下。

### C. 提交并推送 / 同步 / 强推

1. 点「提交」右侧的 `▾`，在卡片内部展开三行（不是新页面）：
   `提交并推送` / `提交并同步` / `提交并强推（with lease）`。
2. 每行右侧显示不可用原因（`未发布` / `分支已是最新` / `需要提交信息`）；不可用不是灰色一坨，而是带原因的可读行。
3. 选完自动收起；`Esc` 收起但不提交。

### D. 同步基准（新需求）

1. ⑤ 收起时卡头就有结论：`基准 origin/main · 领先 3`（绿色 `已合入` 当 0）。
2. 展开看到具体是哪些提交；点「拉取基准分支」→ 卡片内显示进度行，完成后卡头变 `已合入`，④ 里可能出现新的冲突或改动。
3. 树不干净时按钮禁用，卡头下方一行灰字：`先提交或贮藏改动`。

### E. 冲突（唯一会打断流程的状态）

1. ② 出现在最顶部，抢在提交卡之前；③ 的提交按钮变 `disabled` 并显示 `有冲突`。
2. 每个冲突文件一行，右侧三个解决动作：`保留我方` / `保留对方` / `标记已解决`。
3. 解决完最后一个文件，② 底部按钮从 `完成合并`（disabled）变为可用。
4. 中止随时可用，二次确认就地展开（`确定中止？[确定]`）。

### F. 丢弃 / 删除

1. 行内 `🗑` 与组头「全部丢弃」都走**就地二次确认**：该行变红底一行 `丢弃 src/panel.tsx 的改动？[丢弃] [取消]`，不弹窗。
2. 未跟踪文件文案区分：`删除文件`（不可恢复）。

### G. 切仓库 / 切分支

1. ① 的仓库下拉列出 `主仓库 / 子模块 / 嵌套仓库`，脏点标在名字后。
2. 选中子模块后，① 变成 `[子模块 · vendor/lib ▾]`，**提交按钮文案改为 `提交到 子模块 vendor/lib`**（只在这一处提示目标）。
3. 分支下拉就地展开：当前分支打勾，本地/远端分组，底部 `＋ 新建分支`。

### H. 历史 / 贮藏（低频，收起态）

1. ⑥ 展开就是一个列表 + 过滤框，不跳页；展开时其它卡片保持原位，滚轮继续往下就能看到 ⑦ ⑧。
2. 点一条提交 → 就地插入文件清单与只读 diff；再点收起。
3. ⑦ 的新建贮藏是卡头右侧的 `+`，不需要先展开。

## 7. 键盘

| 键 | 行为 |
|---|---|
| `⌘/Ctrl + Enter` | 提交（信息框内） |
| `Esc` | 收起当前展开的菜单/确认行；不提交、不丢弃 |
| `⌘/Ctrl + K` | 聚焦历史过滤（展开 ⑥ 并聚焦） |

## 8. 空态与边界

| 情况 | 呈现 |
|---|---|
| 工作区干净 | ③ 塌成 `提交 · 还没有暂存的更改`；④ 显示 `工作区干净` + 一行说明；⑤⑥⑦⑧ 仍可见（能查历史） |
| 非本地工作区 | 整块替换成一句说明 + 「在内置面板打开」，不渲染任何动作 |
| 没有远端 | ① 不显示 upstream 行；⑤ 不渲染；提交按钮只保留「提交」 |
| 远端动作失败 | 卡片原位出现一行红色说明 + `重试`，不清空别的内容 |

## 9. 与 v3 的差异

| 项 | v3 | v4 | 理由 |
|---|---|---|---|
| 导航 | 5 个平级页 + 返回条 | 单页 8 张可折叠卡 | 不再丢失上下文，返回键消失 |
| 已暂存位置 | 页面下半部「已暂存的更改」组 | ③ 提交卡内部 | 提交前一眼确认内容 |
| 提交方式 | 主按钮 + `···` 展开 | 主按钮 + `▾` 就地展开 3 行 | 4 种收尾是一组，不是菜单 |
| 基准分支 | 「更多」页里的卡 | ⑤ 常驻卡（收起态就有结论） | 最高频的「要不要同步」零点击可见 |
| 13 个远端动作 | 独立页铺开 | ① 的 `···` 下拉 | 低频动作不占版面 |
| 历史/贮藏/分支 | 平级页 | 收起态的 ⑥⑦⑧ | 需要时才占空间 |
| 卡片头 | 标题 + 计数 | 标题 · 计数 + 摘要 + 动作 | 收起态也能读懂状态 |

## 10. 落地映射

| 需求 | 现有能力 | 差距 |
|---|---|---|
| 卡片折叠 | `Collapsible` | 无 |
| 文件在两卡间移动 | 现有 `git.stage`/`git.unstage` | 只需 UI 归属逻辑 |
| 提交卡内展开 3 行 | 现有 `commitMenuOpen` | 无 |
| 基准卡 | 已实现（`base` + `git.mergeBase`） | 从「更多」页搬到常驻卡 |
| 冲突行解决动作 | 无 | **需新增** worker：`git.checkoutSide`（ours/theirs）+ 复用 `git.stage` |
| ① 的 `···` 远端动作 | 现有 13 个请求 | 从独立页搬进下拉 |
| 分支下拉 | 现有 `branchList/Switch/Create/Delete` | 从独立页搬进下拉 |
| 就地二次确认 | 现有 `forceConfirm` 模式 | 丢弃确认同样处理 |

**唯一需要新写后端的是冲突解决三动作**，其余全部是现有请求的重新编排。
